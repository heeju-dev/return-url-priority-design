# Return URL Priority Design

여러 경로로 진입할 수 있는 화면에서, "완료 후 어디로 돌아갈지"가 경로마다 다르고 동시에 겹칠 수도 있는 상황을 우선순위 구조로 정리한 사례를 재구성한 기록입니다.

## 문제

결제수단 등록 화면은 진입 경로가 세 가지였습니다.

- **일반 진입**: 서비스 안에서 직접 들어옴
- **외부 서비스 진입**: 다른 서비스에서 성공/실패 복귀 주소를 함께 전달하며 진입 (팝업 또는 페이지 이동)
- **카드/계좌 등록 시스템 왕복**: 화면 안에서 "새 카드 불러오기"를 누르면 외부 등록 시스템을 잠깐 다녀옴

문제는 **이 경로들이 서로 독립적으로 조합될 수 있다**는 점이었습니다. "외부 서비스에서 들어온 사용자가, 화면 안에서 카드 등록 시스템도 한 번 더 왕복하는" 상황이 실제로 발생했고, 이때 사용자가 중간에 이탈하면 정확히 어디로 보내야 하는지가 불명확했습니다.

기존에는 단순히 "뒤로가기"로 처리했는데, 카드 등록 시스템을 왕복한 뒤 뒤로가기를 하면 그 과정에서 쌓인 브라우저 히스토리 때문에 **완전히 무관한 예전 화면으로 튕겨나가는** 문제가 QA로 발견됐습니다.

## 해결 — 우선순위 구조

가능한 경우를 나열하는 대신, 순서대로 확인하는 우선순위 체인으로 정리했습니다.

전체 예제는 [`example.ts`](./example.ts)에 있습니다.

```
1. 외부 서비스가 지정한 이탈 복귀 주소가 있으면 → 그쪽으로
2. 새 창(팝업)으로 열렸다면 → 창을 닫음
3. 카드/계좌 등록 시스템이 돌려준 복귀 주소가 있으면 → 그쪽으로
4. 아무 조건도 안 걸리면 → 기존의 단순 뒤로가기
```

## 왜 이 순서인가

- **외부 서비스 조건을 가장 먼저 보는 이유**: 사용자가 애초에 어디서 왔는지가 가장 "바깥쪽" 맥락이라, 최우선 판단 기준이 되는 게 자연스럽다고 판단했습니다.
- **팝업 닫기가 그다음인 이유**: 팝업은 브라우저 히스토리가 거의 없어서, 여기서 뒤로가기를 시도하면 예측 불가능하게 동작할 위험이 있었습니다. 복귀 주소가 없다면 억지로 이동시키기보다 그냥 닫는 게 안전했습니다.
- **카드 등록 시스템 복귀가 세 번째인 이유**: 이건 "외부 서비스와 무관하게, 일반 진입인데 그 시스템만 갔다 온" 상황에 필요한 것이라, 외부 서비스 조건보다는 낮은 우선순위가 맞았습니다.
- **기존 뒤로가기는 최후 수단으로만**: 아무 정보도 없을 때만 기존 방식을 쓰도록 해서, 새로 추가한 로직이 원래 동작을 깨지 않게 했습니다.

## 검토했지만 채택하지 않은 방법 — 목적지 하드코딩

모든 경로가 결국 같은 화면으로 돌아간다면, 그 주소를 코드에 고정해버리는 게 더 간단하지 않을까 검토했습니다. 채택하지 않은 이유는:

- 외부 서비스 진입 경로는 복귀 정책이 아직 협의 중이라 확정되지 않은 상태였습니다.
- 코드에 고정하면, 나중에 특정 경로만 다른 곳으로 보내야 하는 요구사항이 생길 때마다 하드코딩된 부분을 다시 찾아 고쳐야 합니다.

대신 "각 진입 경로가 원하는 복귀 주소를 값으로 전달하면, 그대로 활용한다"는 방식을 유지해서, 목적지가 우연히 같더라도 그건 각 경로가 그렇게 값을 채워 보냈기 때문이지 코드에 박아놓은 게 아니라는 원칙을 지켰습니다.

## 함께 겪은 시행착오

**파라미터 이름 충돌**: 외부 서비스가 전달하는 파라미터명이, 내부 인증 절차가 이미 쓰고 있던 이름과 겹쳐서 값이 유실되는 문제가 있었습니다. 화면 진입 즉시 내부 전용 이름으로 변환해서 보관하는 방식으로, 이후 어떤 단계를 거쳐도 값이 안전하게 유지되도록 했습니다.

**보안 허용 목록 누락**: 팝업이 부모창에 메시지를 보내는 기능에, 미리 정해둔 도메인 목록에만 전달을 허용하는 보안 장치가 있었습니다. 새로 연동한 외부 서비스가 이 목록에 없어서 로직은 정상인데 메시지가 전달되지 않는 문제가 있었고, 각 단계에 로그를 심어 원인을 좁혀 목록에 도메인을 추가하는 것으로 해결했습니다.

## 배운 점

여러 조건이 동시에 성립할 수 있는 상황에서는, 조건을 나열해서 하나씩 처리하기보다 "어느 조건이 사용자 의도에 가장 부합하는지" 순서를 명확히 정하는 게 예측 가능한 동작을 보장하는 데 중요하다는 걸 확인했습니다.
